## Project Overview

ESP32-S3 intelligent coffee scale with grind-by-weight functionality. Features predictive grinding system, LVGL touch UI, and BLE OTA updates. Automatically grinds coffee beans to precise target weights using flow prediction and pulse correction algorithms.

## Essential Commands

All development tasks use the unified cross-platform Python tool:

```bash
# Build and upload
python3 tools/grinder.py build-upload

# Data analysis (exports data and launches Streamlit report)  
python3 tools/grinder.py analyze
```

**Common Commands:**
- `python3 tools/grinder.py build` - Build firmware only
- `python3 tools/grinder.py upload` - Upload latest firmware via BLE
- `python3 tools/grinder.py export` - Export grind data to database
- `python3 tools/grinder.py report` - Launch Streamlit report from existing data
- `python3 tools/grinder.py scan` - Scan for BLE devices
- `python3 tools/grinder.py info` - Get device system information
- `python3 tools/grinder.py clean` - Clean build artifacts

## Architecture

**4-Layer Architecture:**
1. **Hardware Layer** (`src/hardware/`): ESP32-S3 peripheral abstraction
2. **Control Layer** (`src/controllers/`): Business logic and algorithms  
3. **System Layer** (`src/system/`): State management
4. **UI Layer** (`src/ui/`): LVGL touchscreen interface

**Key Components:**
- **HardwareManager**: Central hardware coordinator
- **GrindController**: 9-phase state machine with predictive flow control, 10 pulse corrections, mechanical instability detection, and time mode additional pulses. Predictive stop uses a per-profile **learned coast time** measured from the first settle after motor stop. The observation MUST divide by the same flow figure the prediction multiplied by (`coast_prediction_flow_gps`) or the units do not cancel and every learned coast comes out short - it previously used the 95th percentile against a mean and read ~25% low, which overshot persistently and could not self-correct. Learning accepts overshoots and undershoots - only the measurement being spoiled (disturbed scale, out of range) or an aborted grind rejects it. Pulse correction converges instead of firing when the remaining error falls below `GRIND_PULSE_MIN_DELIVERY_G`, expressed as a weight rather than a duration so the worst-case undershoot does not scale with flow rate
- **Coast model (`CoastWindow`)**: the last `GRIND_COAST_WINDOW_SIZE` (8) measurements per profile, stored as one NVS blob per profile (`coastw0..2`) and predicted from with an **order statistic** - `GRIND_COAST_RANK_FROM_TOP` (1 = the highest of the window) plus a small `GRIND_COAST_TAIL_PAD_S`. A high quantile rather than an average because the cost is one-sided: coffee in the chute can be topped up by a pulse, coffee in the cup cannot be taken back, so being beaten by half of all grinds - which is what an average guarantees - is the wrong target. It replaced an EWMA plus safety factor. **Do not reintroduce an averaged estimate with direction-dependent learning rates**: any accumulator nudged harder one way than the other ratchets, and the symptom is hunting (creep down over several grinds, one overshoot, a large correction down, creep back up) that never settles. A window cannot hunt, because the predicted value is always a measurement the grinder really produced and can never leave the range of observed behaviour. Legacy single-value `coast0..2` keys are read once to seed the window and never written again
- **LoadCell (HX711)**: Multi-mode precision weight measurement (instant, smoothed, filtered), calibration flag, noise diagnostics. The control-path reading (`get_weight_low_latency`) uses a **least-squares fit** over `SYS_CONTROL_FIT_WINDOW_MS` evaluated at the newest sample - noise reduction without the lag of a moving average. A 100ms window at 10 SPS held a single unfiltered sample. Sudden-event detection must keep using `get_instant_weight()`; smoothing spreads a step below the detection threshold
- **DiagnosticsController**: System health monitoring (calibration status, sustained noise, mechanical instability, low memory), state persistence, hysteresis, priority-based warnings. `LOW_MEMORY` samples internal DRAM free size and largest free block every 5s - internal heap is what actually exhausts, since `ESP.getFreeHeap()` includes PSRAM and stays healthy until an allocation fails
- **UIManager**: 7 screens with LVGL integration; menu page surfaces quick Tools (Scale view, Calibrate, Tune Pulses, Motor Test) followed by Settings (Bluetooth, Display, Grind Settings) and Info sections (Diagnostics, System Info, Logs & Data, Lifetime Stats), warning icon indicator, split-button layout for time mode pulses
- **StateMachine**: Central state coordination (READY → GRINDING → GRIND_COMPLETE)

**Update Intervals:** 20ms grind control, 25ms load cell (active), 50ms UI/hardware

**Grind session logging (schema 3):** the control loop (50Hz) logs a row carrying the filtered weight AND the raw HX711 sample with its sequence number and age - but only when some value in the row differs from the last logged one (new sample, a sample ageing out of a filter window, motor or phase edge, flow, stop target). Rows identical except for the clock are skipped: at 10 SPS most 50Hz rows were exact repeats, and without skipping them 50 grinds did not fit the partition. The comparison is exact, so every value the controller acted on stays reconstructible; row spacing is therefore uneven, and analysis must use sample times, not row counts. A row holds a NEW sample only when `raw_sample_seq` changes - de-duplicate on it. Each session stores the grind's `tare_offset_raw` and `cal_factor` (grams = (raw - tare) / cal). Sessions are saved only while the menu's Logging toggle is on, which now defaults ON (`GRIND_LOGGING_ENABLED_DEFAULT`) - it defaulted off, which left nothing to export. Retention is up to 50 sessions and bounded by free LittleFS (`SESSION_STORAGE_RESERVE_BYTES`); with repeated rows skipped a ~30s grind is roughly 25KB, so 50 fit alongside the 256KB persistent log and the reserve without changing partitions (the 3MB LittleFS partition sits directly before `patch`, so growing it needs a new partition table - USB-only, and it reformats LittleFS); cleanup runs BEFORE writing, since running it only after a successful write let a full partition stop logging permanently. `tools/grinder.py export` now MERGES into the database (fingerprinting each file) instead of replacing it, so history accumulates beyond what the device holds. `tools/analysis/noise_breakdown.py` splits noise into load cell / vibration / grinding using motor-off, motor-on-before-grounds-arrive, and grinding segments. Struct changes are schema-versioned - see `tools/ble/CLAUDE.md`; do not purge to work around them.

**Burst before target (`GRIND_BURST_*`, phase `BURST`, NVS `burstw`):** grounds pile up in the chute as a mound and trickle out late. Every weight grind (except the knock test) therefore stops its main run short and shakes the mound loose before the scale is read: the predictive phase aims at `target - expected burst - GRIND_BURST_MARGIN_G` (0.05g) via `get_predictive_target_g()`, and the predictive stop goes straight to `BURST` with no settle in between. `BURST` waits `GRIND_BURST_OFF_MS` (250ms, so the first jolt is a start rather than more grinding), then sends `GRIND_BURST_PULSES` (5) jolts as one pulse train, each as long as the motor latency learned by Tune Pulses (`get_jolt_ms()`), 250ms apart; when the train is done it goes to `PULSE_SETTLING`, and correction carries on exactly as before. Example: burst expected 0.10g, target 18.5g -> main run aims at 18.35g. **What a burst delivers cannot be measured in an ordinary grind**, because it lands in the same settle as the coast. It is measured by the knock test instead and kept as a `PulseWindow` of grams (median; `GRIND_BURST_SEED_G` 0.20g until one is measured - 3 jolts measured +0.15g, and too high only stops earlier). The coast observation subtracts the expected burst from the settled tail (`[BURST] Tail = coast + expected burst`), so the coast window keeps holding coast and the next prediction adds the burst back: the total the main run stops short by remains a tail the grinder really produced, even when the burst figure is off. A burst that cannot start is skipped and nothing is subtracted. The mechanical-instability monitor ignores `BURST`. Correction pulses now follow a burst, so the pulse model learns post-burst extras. Report section `[BURST MODEL]`.

**Chute Knock Test (Menu → Tools):** measures the burst, for the burst model. A real weight grind (`GrindSessionDescriptor::knock_test`, session flag `GRIND_SESSION_FLAG_KNOCK_TEST`) to `KNOCK_TEST_TARGET_G` (18.5g) with beans in the hopper, using the active profile, and no burst after its main run. The predictive stop aims `KNOCK_TEST_STOP_SHORT_G` (0.5g) low. At the first settle, `run_pulse_decision_phase` hands over to `begin_knock()`: phase `KNOCK_TEST` fires exactly the burst (`GRIND_BURST_PULSES` jolts of `get_jolt_ms()`, `GRIND_BURST_OFF_MS` apart); after the last one it waits 1s and reads the scale the way the pulse decision does (stopped rising, same backstop), then returns to `PULSE_DECISION`, which finishes the dose with ordinary correction pulses. Released = settled after minus settled before; it is pushed into the burst model if plausible (`GRIND_PULSE_DELIVERED_MIN_G..MAX_G`), persisted at session end like the pulse model, logged as `[KNOCK]`/`[BURST]` lines, shown as a notice during the grind and in a dialog on COMPLETED with the new model value, final weight and correction count. If the jolts cannot start, the dose is finished without them. Nothing else is learned: the coast is recorded in the history as rejected (`knock test`) and its pulses are not added to the pulse model. `observe_coast()` runs once per grind (`coast_observed_`), because the decision is entered a second time after the knock. The mechanical-instability monitor ignores `KNOCK_TEST`. The session counts for grind freshness (it grinds beans), is always saved, is excluded from statistics, and is skipped by `noise_breakdown.py`. Both test dialogs restore the ready screen to the profile's grind mode, since the grind events set the UI mode to the test's own. The jolts use `Grinder::start_pulse_train()`, built by `build_pulse_train()` in `src/hardware/pulse_train.h`: one RMT transmission, every period split into <=32767us halves, no hardware looping, completion judged by the clock then confirmed once with `rmt_tx_wait_all_done(..., 50)` - polling it with a zero timeout logs an error on every call. **Pulse lengths are exact.** `start_pulse_rmt()` sends a one-pulse train through `build_pulse_train()`. It used to get every pulse over 65.5ms wrong - it looped one symbol containing the remainder, and the driver treats `loop_count` 0 and 1 as a single transmission - so on the user's grinder 70-77ms corrections went out at 38-45ms. That was only fixed together with the pulse delivery model below, because exact pulses planned from flow alone overshoot (simulated: 35% of grinds vs 23% with the bug, 5% with the model). Still not fixed, deliberately: `is_pulse_complete()` uses `digitalRead()` on the RMT-driven pin, whose input buffer is not enabled, so it returns LOW at once - every logged PULSE_EXECUTE lasts one 20ms cycle and the motor is logged as off for the rest of the pulse. PULSE_SETTLING's wait (flow latency, ~400ms, + 200ms) normally covers it; the user wants changes to grind timing approved first.

**Pulse delivery model (`PulseWindow`, NVS `pulsew`, one for the grinder):** a pulse delivers more than its grinding time (length past the learned motor latency) x flow, because the start-up jolt also shakes retained grounds loose - measured 0-0.10g extra on this grinder. Each pulse after the first settle is observed (`observe_pulse`: delivered minus flow x grinding time, using the same flow figure the plan used; rejected if the scale was disturbed or delivery is implausible) and the last 8 kept. Pulses are planned as `latency + max(0, needed - extra) / flow`, where `needed` is to target - tolerance as before and `extra` is the window's UPPER QUARTILE (`GRIND_PULSE_PLANNING_QUANTILE`), so pulses tend to come out short and a second correction finishes - the user prefers two corrections to one too large. Never shorter than the learned latency from Tune Pulses. If even that shortest pulse is expected (median extra) to pass target + tolerance, the grind finishes instead. Extra is floored at zero, so the model can only shorten pulses. Seeded at 0.06g (the median of the user's logged pulses) until a pulse is measured. Persisted at session end on COMPLETED and TIMEOUT. Logged as `[PULSE]` plan/observation lines; the report has a `[PULSE MODEL]` section.

**Negative-weight failsafe:** requires `GRIND_NEGATIVE_WEIGHT_CONFIRM_SAMPLES` (4) consecutive RAW samples below -1g, counted on `get_raw_sample_snapshot()` converted with the live tare and cal factor. It used to fire on a single 20ms cycle of the filtered weight, and one corrupted HX711 read (no checksum; data lines next to the motor relay) ended grinds with "Err: neg wt -4xx". Counting the filtered weight would not fix that: the least-squares fit spreads one bad sample over ~3 filtered values. A run that ends before the limit logs `[FAILSAFE] Ignored N implausible sample(s)`.

**Persistent history and log (survive any restart, including a manual one after a hang):**
- `/history.bin`: the coast history (10 grinds) and error history (10), each entry stamped with a boot number. Loaded in `GrindController::init()` (LittleFS is mounted first in `main.cpp`), saved by the file IO task after every END/DISCARD session op - written to `/history.tmp` then renamed, with the temp file as a fallback on load. Core 0 history writes and the Core 1 snapshot share `history_mux_`; entries are built outside the lock and published inside it. Records are dropped (boot counter kept) if a struct layout changed. Factory reset deletes it.
- `/logs/log_NNNNN.txt`: every `LOG_BLE` line is staged in a 16KB PSRAM ring and appended by the file IO task every 5s (or at 4KB). 32KB segments, at most 8 (256KB); the oldest segment is deleted BEFORE a new one is started and before any write that would leave less than 64KB free - if only the current segment is left, it rolls to a fresh one and deletes the old, so the newest lines are always kept. Each boot starts its own segment behind a `===== BOOT | reset: <reason>` marker. Task heartbeats are kept in full only while a grind is active (the grind-control heartbeat shows phase and weight) and one round per 10 minutes otherwise - matched on HEARTBEAT inside the leading tag, since `TASK_HEARTBEAT_<name>]` does not end in `_HEARTBEAT]` and would have caused ~360 flash writes an hour. Every phase transition is logged as `[PHASE] A -> B at t, weight` (it was only logged under `ENABLE_GRIND_DEBUG`, which is off). The report's `[PREVIOUS BOOT LOG]` shows the last 3KB the previous boot wrote. Session purge does not touch either file.

**Diagnostics (`generate_diagnostic_report`, pulled over BLE):** carries `[CRASH DUMP]` (placed first, so a report that fails partway still shows why), `[MEMORY]`, `[STACK HEADROOM]`, `[ALGORITHM STATE]`, `[COAST MODEL]`, `[RECENT ERRORS]`, and `[BOOT LOG]`.
- **`[COAST MODEL]`** prints each profile's stored window sorted, the quantile it selects and the padded prediction, then the last 10 grinds since boot as two lines each: what was predicted against what was measured, and where the dose landed (final vs target, signed error, `OVERSHOOT` marker, pulse count). Both halves are recorded per grind rather than derived later, because the window has already moved on by the time anyone reads the report. Only the window survives a reboot; the per-grind history is RAM-only
- **Crash dump**: `debug_log_printf` rolls every log line into a ring in RTC memory, which a panic or watchdog reset does not clear. Nothing is written while running - on the next boot the reset reason decides whether the survivors are kept. Costs nothing from the heap (RTC is a separate region) and never touches flash. Do NOT log inside per-packet loops: `send_chunk` used to, and a single report buried the ring in over a kilobyte of "TX: n bytes"
- **Report timing**: notifications are paced by the client's connection interval, so a few hundred packets can take a minute. The flasher times out on 15s of silence, not on total elapsed time; a fixed budget failed healthy transfers for being long
- **Stack headroom** is reported per task because exhausting a stack corrupts memory rather than failing cleanly. Measured: Bluetooth needed ~4KB (it was on a 4KB stack), UIRender ~7KB

**Bluetooth on/off (`BluetoothManager`):** the NimBLE stack and GATT server are built on the first `enable()` of a boot (`build_gatt_server()`, `stack_ready`) and never torn down. `disable()` - the menu toggle or the auto-disable timeout - only stops advertising and drops a connected client (by `getConnId()`, not by copying the server's peer map, which the host task edits); `enable()` after that just advertises again. **Do not bring back `BLEDevice::deinit()`**: in Arduino-ESP32 3.3.x, `deinit(false)` stops NimBLE but keeps the library's private static `m_pServer`, so the next `init()`/`createServer()` hands back that stale server - already marked started, its GATT tables registered with a host that no longer exists - and skips `ble_gatts_reset()`. Re-enabling Bluetooth from the menu after the auto-disable panicked the grinder that way. Keeping the stack costs ~65KB of internal heap for the rest of the boot (it is built at boot by default anyway); ~108KB stays free, well above the 40KB `LOW_MEMORY` threshold. `BluetoothManager::log()` goes through `debug_log_printf`, so BLE lifecycle lines reach the crash ring and the persistent log.

**Threading model (load-bearing):** GrindControl and WeightSampling run on **Core 0**; LVGL/UIRender runs on **Core 1**. Two rules follow:
- **All phase transitions and all motor calls happen on Core 0 only.** UI-facing methods (`stop_grind`, `return_to_idle`, `continue_from_purge`, `pause_time_grind`, `resume_time_grind`, `start_additional_pulse`) merely set an atomic request; `process_ui_requests()` applies them at the top of `update()`. Doing the work inline from Core 1 races two ways: phases that re-assert the motor each cycle (PRIME) switch it back on right after a stop, and the RMT calls delete/recreate a shared encoder, so concurrent calls double-free it
- **No blocking flash writes in `update()`.** Session NVS writes ride on `FlashOpRequest` and land in the file IO task


**Grind Phases:**
- Standard phases: IDLE, INITIALIZING, SETUP, TARING, TARE_CONFIRM, PRIME, PRIME_SETTLING, PREDICTIVE, PULSE_DECISION, PULSE_EXECUTE, PULSE_SETTLING, FINAL_SETTLING, TIME_GRINDING, COMPLETED, TIMEOUT
- `BURST` - Jolts straight after the predictive stop, before the first settle (see Burst before target). Appended as id 20, after `PURGE_CHECK` (18) and `KNOCK_TEST` (19)
- `TIME_ADDITIONAL_PULSE` - Dedicated phase for post-completion additional grinding pulses in time mode
- `PURGE_CONFIRM` - Pauses after chute operation (in Purge mode) to allow user to discard grinds before continuing to main grind
- **Timeout**: 60-second maximum from grind start (includes taring), auto-stops and requires user acknowledgment

**Grinder Purge/Prime:**
- **Always runs** before weight-mode grinding to saturate the grinder for accurate latency detection
- **Prime mode**: Keeps coffee, continues immediately to PREDICTIVE phase
- **Purge mode** (default): Shows confirmation popup, waits for user to discard stale grinds, then continues
- **Configurable amount**: 0.1g-5.0g (default 1.0g), replaces old hardcoded `GRIND_PRIME_TARGET_WEIGHT_G`
- **Purge popup**: "Keep purge grinds from now on" checkbox switches mode from Purge → Prime in preferences
- **Purge check (`PURGE_CHECK`)**: confirming the purge no longer starts the motor directly. `PURGE_CONFIRM` pauses the control loop and the UI leaves the popup the moment ✓ is tapped - often while the portafilter is still being seated - so the decision happens in its own phase once the reading holds steady (0.2g peak-to-peak over 500ms, 3s fallback). The reading is compared with what the purge actually DELIVERED (settled, recorded at `PRIME_SETTLING`), not the configured amount. More than `GRIND_PURGE_RETARE_THRESHOLD_G` (0.5g) apart = grounds discarded and the basket re-seated, so it re-tares (`TARING` → `TARE_CONFIRM` → straight to `PREDICTIVE`, skipping a second prime) and the session gets `GRIND_SESSION_FLAG_RETARED_AFTER_PURGE`. Within it = grounds kept, and the grind continues counting them as before. Below -20g the portafilter is off the scale: it waits and never tares an empty cradle. `PURGE_CHECK` is excluded from the -1g negative-weight failsafe, since about -1g after dumping is exactly what the re-tare corrects. It was appended to `GrindPhase` rather than inserted - phase IDs are stored in session logs

**Vibration Test (Menu → Tools):** a time-mode session (`GrindSessionDescriptor::vibration_test`) with an empty hopper: 3s motor off after the tare, 5s motor on, then final settling. Core 0 computes per-sample noise for motor-off and motor-on from raw counts (`NoiseAccumulator`, offset-immune so the tare cannot disturb it), skipping 500ms after each motor start/stop, and flags grounds if the weight rises >0.3g. The result is shown in a dialog on COMPLETED. The session is always saved (whatever the logging toggle), is flagged `GRIND_SESSION_FLAG_VIBRATION_TEST`, and is excluded from statistics and from grind freshness - otherwise an empty-hopper run would make stale grounds look fresh and skip the next purge. Dialogs must never be raised from inside a confirm-dialog callback: the confirm controller clears all callbacks when that callback returns, leaving the new dialog's buttons dead - check preconditions before showing the first dialog
- **Logging disabled** during PURGE_CONFIRM phase to avoid capturing data while paused
- **Preferences**: `chute_mode` (int: 0=Prime, 1=Purge, default=1), `chute_amount_g` (float: 0.1-5.0, default=1.0)

**Time Mode Pulses:** Split-button completion screen (OK + PULSE), `TIME_ADDITIONAL_PULSE` phase, 100ms duration

**Grind Settings:** Configurable through Menu → Grind Settings page
- **Mode Selection**: Radio buttons for Weight/Time mode selection
- **Swipe Gestures Toggle**: Enable/disable vertical swipe gestures for mode switching (default: disabled)
- **Automation**: Start on Cup and Return on Removal toggles, plus a **Min. weight** slider (stepping through fixed options: Off / 200 / 400 / 500 / 600 / 700 g, see `MenuScreen::kMinWeightOptions`) that is the auto-start trigger itself - the grind begins when the scale settles above it. 0/Off disables auto-start entirely. Re-arms only after the weight drops 100g below the threshold and stays there 2s. Weight is measured against the empty-cradle reference stored at calibration (`hx_empty`), NOT the working tare - a grind zeroes with the portafilter in place, so the tare says nothing about what is on the scale. Steadiness uses peak-to-peak range over the window (`USER_AUTO_GRIND_STABLE_RANGE_G`), NOT `is_settled()`: that is 0.010g std dev, right for weighing a dose but far too tight for a 600g portafilter, and every brief excursion restarted the dwell so the trigger fired erratically
- **Purging**: Radio buttons (Prime/Purge) and Amount slider (0.1g-5.0g)
- **Preferences**: `swipe.enabled` (boolean), `grind_mode` (0=Weight, 1=Time), `chute_mode` (0=Prime, 1=Purge), `chute_amount_g` (float), `time_use_scale` (boolean, time-mode display only), `autogrind.min_weight_g` (int, 0=auto-start disabled)
- **Behavior**: Swipe gestures only work when enabled; direct mode selection always works
